Last updated: 2026-05-11

This file is the source of truth for what is real, what is simulated, and what still needs to be made production-real. Do not remove or soften an item because it makes the demo look better. Update the status only after code and tests prove the claim.

## Current Truth Summary

FireGuard is a real hosted Cloud Run app with a real FastAPI backend, real Next.js frontend, real Elastic-backed operational memory, a real managed Fivetran Connector SDK connection syncing into BigQuery, source-backed public BC emergency context snapshots, real Vertex Gemini calls, a real managed Vertex AI Agent Engine deployment, real Twilio allowlisted SMS execution, real Twilio inbound SMS opt-in handling, real GitHub Issues task creation for approved shelter/road/dispatch actions, real OpenTelemetry span export to a self-hosted Arize Phoenix service on Cloud Run, and real duplicate OTLP export to Arize AX using the provided Arize Space ID/API key. The self-hosted Phoenix deployment now uses Cloud SQL PostgreSQL, so traces survive Cloud Run replacement. Eval results are exported as Phoenix spans and Arize AX OTLP spans; Phoenix annotation IDs are only claimed for eval runs where the API returns an annotation ID. Phoenix Cloud REST is not claimed; the verified hosted Arize path is Arize AX OTLP at `https://otlp.arize.com/v1/traces`.

FireGuard is not yet a fully real emergency orchestration system. The demo-critical evacuation scenario still uses some synthetic operational records, but the evacuation-zone geometry, zone population/home counts, Fivetran-loaded FIRMS fire evidence, road-closure evidence, and zone vulnerability/access context are now source-backed rather than invented rows. Shelter B capacity is read from a shared Google Sheets operator feed owned outside the app; it is a real auditable operator input, not an official public ESS capacity feed unless that sheet owner is authorized by the operating agency. Unconfirmed shelter capacity values are now treated as confirmation gates rather than official numeric evidence. Shelter A and Shelter C remain closed ESS records and their capacities are not used for evacuee intake. Zone vulnerable-count and evacuation-access values are now sourced from Statistics Canada 2021 Census Profile age structure and the BC Digital Road Atlas WFS. This is a real public-source proxy, not an official vulnerable-person registry, household vehicle-ownership feed, or official transport-access score. The older Google Sheets zone-operations feed remains connected as an operator-input path, but it is no longer the winning source after the source-backed sync. Zone B and Zone C resident test contacts are real Twilio inbound SMS opt-ins from allowlisted test recipients; they are still not official resident registries.

Current live BC FIRMS data does not presently threaten the configured historical demo zones. Hosted assessment on `2026-05-08T12:32:26Z` correctly returned `recommended_strategy=monitor`, `requires_approval=false`, `store_backend=elastic-mirrored`, 25 current FIRMS rows, one internal `incident_timeline_update`, no public SMS, no shelter notification, no road-ops task, and no dispatch task. The dramatic route-rejection evacuation demo remains a labeled replay of real source snapshots unless a current live wildfire actually intersects the configured zones or routes.

Hybrid mode is now implemented so judges can see current live data without corrupting the replay evidence. Hosted `/sync/live-overlay` on `2026-05-09T13:35Z` returned Fivetran BigQuery-backed current live records in separate Elastic indices: `fire_hotspots=32`, `fire_perimeters=54`, `road_events=84`, and `weather_observations=14`, all marked `decision_eligible=false`. The run returned `source_provider=fivetran`, `provider_path=fivetran_bigquery`, `fallback_active=false`, and one data-quality warning excluding 21 rectangular FIRMS rows outside the official BC boundary. Hosted `/incidents/current` then returned `mode=hybrid`, `decision_context_mode=replay_snapshot`, live counts `32/54/84/14`, and `live_provider_paths=["fivetran_bigquery"]`. This is real current-source visibility through Fivetran beside replay decision evidence, not a claim that the current live records caused the replay evacuation plan.

Every demo claim must be backed by one of:

- a live provider call;
- a stored real source snapshot with provenance;
- a synthetic/simulated label visible in code, API output, and UI.

If none of those is true, the claim does not belong in the demo script.
