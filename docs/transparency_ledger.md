# FireGuard Transparency Ledger

Last updated: 2026-05-07

This file is the source of truth for what is real, what is simulated, and what still needs to be made production-real. Do not remove or soften an item because it makes the demo look better. Update the status only after code and tests prove the claim.

## Current Truth Summary

FireGuard is a real hosted Cloud Run app with a real FastAPI backend, real Next.js frontend, real Elastic-backed operational memory, a real managed Fivetran Connector SDK connection syncing into BigQuery, source-backed public BC emergency context snapshots, real Vertex Gemini calls, a real managed Vertex AI Agent Engine deployment, real Twilio allowlisted SMS execution, real Twilio inbound SMS opt-in handling, real GitHub Issues task creation for approved shelter/road/dispatch actions, real OpenTelemetry span export to a self-hosted Arize Phoenix service on Cloud Run, and real duplicate OTLP export to Arize AX using the provided Arize Space ID/API key. The self-hosted Phoenix deployment now uses Cloud SQL PostgreSQL, so traces survive Cloud Run replacement. Eval results are exported as Phoenix spans, attached back to those traces as Phoenix `fireguard_eval` annotations, and also exported as Arize AX OTLP spans. Phoenix Cloud REST is not claimed; the verified hosted Arize path is Arize AX OTLP at `https://otlp.arize.com/v1/traces`.

FireGuard is not yet a fully real emergency orchestration system. The demo-critical evacuation scenario still uses replay and some synthetic operational records, but the evacuation-zone geometry, zone population/home counts, fire evidence, and road-closure evidence are now stored from real source snapshots rather than invented rows. Shelter B capacity is now read from a shared Google Sheets operator feed owned outside the app; it is a real auditable operator input, not an official public ESS capacity feed unless that sheet owner is authorized by the operating agency. Shelter A and Shelter C remain closed ESS records and their capacities are not used for evacuee intake. Resident test contacts can now be updated through operator check-ins or real Twilio inbound SMS opt-in; these are real auditable operational inputs, not official resident registries.

## Rule For Future Changes

Every demo claim must be backed by one of:

- a live provider call;
- a stored real source snapshot with provenance;
- a synthetic/simulated label visible in code, API output, and UI.

If none of those is true, the claim does not belong in the demo script.
